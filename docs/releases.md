# Release rings and GitHub Actions

**Staging -> production.** These are the only two cloud environments in the pilot. Run tests and offline agent replays on developer machines and CI runners, not in a third deployment. Build one image on `main`; production uses the exact digest exercised in staging. Cloud operations are disabled until the activation checklist is complete.

### Rings, exposure and admission

| Destination | How it receives a release | Hold, promote or roll back |
| --- | --- | --- |
| **Staging** | After verification on protected `main`, publish one image to ACR, attest its `sha256:` digest, then deploy it automatically. Use a low-capacity API/worker, synthetic records, an email sink and Stripe test mode. Scale down between releases. | Require **30 minutes and five completed journey checks** for the currently staged commit/digest: (1) sample/reset with no model calls, (2) evidence confirmation through mock/debrief/retry, (3) free cap and tenant isolation, (4) Stripe test checkout, renewal, cancellation and webhook replay, (5) compatible migration, worker delivery and notification. A changed agent policy also needs an approved budgeted staging eval. Missing evidence means hold. |
| **Production** | A human requests and approves promotion. Probe the new revision before switching traffic and worker routing; keep the previous compatible revision available. No intermediate customer cohort or additional ring. | Smoke the public endpoint and an async journey; compare errors, latency, usage debits and unit cost to the prior release. On failed smoke, contain exposure, restore the known-good routing and alert. Never promote the stable pointer on a failed check. |

Keep data, credentials, queues and notification destinations separate. Pin prompt, rubric, model routing and price-policy versions at session creation; ring membership grants no paid features. Run one scheduler lease, use compatible queue envelopes, and stage migrations as expand -> backfill -> switch -> contract **after** the rollback window. Use the [livesite objectives](operations.md#observability-alerts-and-livesite) to page for regressions; isolation errors, duplicate charges, or loss of accepted answers warrant immediate action.

### The workflow inventory

| Workflow | Trigger and responsibilities |
| --- | --- |
| [verify.yml](../.github/workflows/verify.yml) | PR, manual, or called by release. Read-only workflow lint, release policy tests, infrastructure fixtures, and application tests/offline replays when available. No production identity or paid model calls. |
| [release.yml](../.github/workflows/release.yml) | Protected `main` push or dispatch: verify, build once, publish with SBOM/provenance, attest, and call the ring workflow for **staging only**. Copy the commit and digest from the run summary; retry a deployment without rebuilding. |
| [ring.yml](../.github/workflows/ring.yml) | Promote or roll back one ring. Require a merged source commit, signed digest from the trusted `main` build and applicable receipt. Protected production approval is separate from staging. Serialize mutations per environment. |
| [infra.yml](../.github/workflows/infra.yml) | Manual Bicep what-if for staging or production; no apply by default. Protected apply repeats the preview for the same commit, deployment name, group and subscription. Reject missing, empty, changed, unsupported or destructive resource plans. Public summaries expose counts and a fingerprint, not resource payloads. |
| [checks.yml](../.github/workflows/checks.yml) | On-demand observation of **one** selected ring, or an explicitly approved, spend-capped model eval in staging. No scheduled Actions runner or paid eval on idle days. Use Azure Monitor for continuous production paging. Application schedules never run in Actions. |

### Release and incident procedure

1. Verify staging shows the published image and all applicable checks. Once it has baked, run `gh workflow run checks.yml --ref main -f task=monitor -f ring=staging` to refresh the observation. The workflow does not occupy a runner during the bake.
2. Request `gh workflow run ring.yml --ref main -f operation=promote -f ring=production -f commit="$commit" -f digest="$digest"`. A missing or stale receipt blocks the request even with approval. Inspect post-switch health and worker routing before declaring success.
3. For rollback, dispatch the same workflow with `operation=rollback`, the destination ring's **previously healthy** commit/digest, and `-f reason="incident reference"`. Do not put customer data in the reason. Freeze promotion, check schema compatibility, restore routing and defaults for new sessions, smoke, then record the outcome. Never rewind invoices, settled usage or the database.

The [admission policy](../scripts/check-release.mjs) reads `rings/staging/current.json` for production promotion, or immutable `history/<ring>/<commit>/<digest-hex>.json` for rollback. Require the matching ring, commit, digest and `deploymentId`, `status: healthy`, and `criticalChecksPassed: true`. For promotion, `completedChecks` and UTC `deployedAt` / `observedAt` must satisfy the staging gate; observations are valid for at most two hours. Reset counts and the clock on redeploy. Keep at least the last two known-good releases and their evidence for 30 days.

The [job runner](../scripts/invoke-ops-job.ps1) passes `operation ring commit digest actions_run_id` to a separately trusted control job and waits for **that execution**. The controller must take a plane lease, re-read evidence, freeze flag and target generation under the lease, reject superseded promotions, perform idempotent changes, smoke and journal the outcome. Observers may refresh only the deployment they actually inspected. Evals must verify the exact staged release and use synthetic/licensed fixtures with a spend ceiling (proposed $2/run); budget exhaustion is not a pass. A timeout is an unknown outcome: inspect the job and durable journal before replay. Deduplicate by operation, ring, commit, digest and run ID.

### Activation checklist

1. The studio now has a root `Dockerfile`, an additive SQLite upgrade, `/healthz` (including version), `/readyz`, and offline candidate-journey checks. These do **not** constitute a production deployment. Before cloud activation, supply and exercise the production persistence/backup strategy, independent control jobs, private release storage, ACR and `infra\bicep\main.bicep` with **only** `parameters\staging.json` and `parameters\production.json`. Verify TLS, trusted origin, restore and private endpoint reachability without exposing the DB. Never use a container's ephemeral SQLite filesystem for real candidate data.
2. Publish and protect `main`, make it the GitHub default before using workflow dispatch, require PR verification, and protect workflow/policy changes. `build`, `model-eval`, `monitor-<ring>` and `infra-{plan,apply}-<ring>` are GitHub identity/approval boundaries, **not additional cloud environments**. Require approval for production, paid evals and infra apply. With one maintainer, document who can approve; do not disable the evidence gate. Check [reviewer](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments) and [attestation](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations) availability before moving to a private repo.
3. Bind [OIDC identities](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-azure) to protected environments. Set `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`; build needs `ACR_NAME` and scoped push. Ring identities need registry/`RELEASE_STORAGE_ACCOUNT` read and scoped `OPS_JOB`/`OPS_CONTAINER` start/inspect in `AZURE_RESOURCE_GROUP`. [Job overrides](https://learn.microsoft.com/en-us/azure/container-apps/jobs) make job-start permission privileged; isolate deploy, observe and eval identities. Never supply runtime model keys or Stripe secrets to CI. The attesting build must use a GitHub-hosted runner.
4. `INFRA_ENABLED`, `RELEASES_ENABLED`, `MONITORING_ENABLED` and `LIVE_EVALS_ENABLED` are repository variables, false/unset by default. Enable only what is needed. Inspect the full [what-if](../scripts/infra-plan.sh) privately (CLI 2.76+, `ProviderNoRbac`): a `Modify` may remove a field. Exercise failure, stale evidence, timeout, duplicate webhook and real rollback in **staging** before enabling production. Include registry retention, Actions and monitoring costs in the pilot budget.
